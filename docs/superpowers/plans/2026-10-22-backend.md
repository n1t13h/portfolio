# Portfolio Backend Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the FastAPI backend in `backend/` that serves the photography portfolio and lets the single admin curate it behind password + TOTP.

**Architecture:** Thin routers call services; services hold all logic and talk to the database (SQLAlchemy) and to external systems only through small interfaces (`Storage`, `UnsplashClient`, `Notifier`) that have in-memory fakes for tests. Image bytes never pass through the API on upload (presigned R2 PUT); the API only reads the uploaded JPEG back to build variants.

**Tech Stack:** Python 3.12, FastAPI, SQLAlchemy 2.0 (sync) + Alembic, SQLite, Pydantic v2 + pydantic-settings, boto3 (R2 S3 API), Pillow, argon2-cffi, pyotp, httpx, pytest, ruff, mypy, uv. Caddy + systemd for deploy.

**Spec:** `docs/superpowers/specs/2026-10-22-backend-design.md`

**Repo rule:** Do NOT `git commit` anywhere in this repo (the owner commits). Leave changes in the working tree; there are no commit steps below.

## Maintainability rules (apply to every task)

- Layout: `backend/app/{api,services,models,integrations,core}`; routers contain no business logic; one responsibility per file; no file over ~300 lines (split by responsibility if it grows).
- Full type hints; `ruff check`, `ruff format --check` and `mypy --strict app` must pass at the end of every task.
- External systems are reached only through the interfaces in `app/integrations/`; services take them as constructor/function arguments, never import boto3/httpx directly.
- Config only via `app/core/config.py` (`Settings`); no `os.environ` elsewhere.
- Each task adds tests with its code; `pytest` stays green after every task.
- Short module docstring stating the module's single job; comments only for non-obvious "why".
- `backend/README.md` documents setup, env vars, running, tests, deploy, and is updated by the task that introduces each.

## Global Constraints

- Upload types: JPEG only, verified by decoding, never by extension/content-type.
- Variants: WebP at 800 / 1600 / 2400 px long edge; download copy: JPEG 2400 px long edge; GPS and other EXIF stripped from every public file.
- Originals only in the private bucket; never publicly reachable.
- `allow_download` defaults to false; false or draft photo → download endpoint returns 404.
- Session cookie: HttpOnly, Secure, SameSite=Strict, short lifetime, plus custom-header CSRF check on state-changing admin calls.
- Admin routes live under `/a/{ADMIN_PATH_PREFIX}`; the prefix is a long random config value; there is no signup route.
- One uvicorn worker; must fit in 512 MB–1 GB with Caddy; images are processed one at a time.
- Unsplash demo limit is 50 requests/hour; sync honours `X-Ratelimit-Remaining`, stops cleanly, resumes next run; one sync at a time.
- Hostnames: frontend `portfolio.ntshptl.in`, API `api.ntshptl.in`, photos `cdn.ntshptl.in` — all config values.
- Public responses carry `Cache-Control` and `ETag`.

## Review Focus

1. A file named `.jpg` that is not a JPEG, is corrupt, or is a decompression bomb → rejected with 4xx, nothing stored (Task 4, 6).
2. Draft photos/collections never appear through published collections, chapter listings, or the download endpoint (Task 8).
3. Reorder requests with missing, duplicate or unknown ids → 422 and no partial change (Task 6, 7).
4. TOTP code replay inside its validity window, and lockout after repeated failures (Task 5).
5. Telegram failure on a contact message → message still saved and 2xx returned (Task 9).
